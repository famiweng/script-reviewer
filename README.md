## 🎯 设计哲学与解决痛点

在传统的长篇影视剧本审稿中，行业常面临三大瓶颈：
1. **单次输入全量长文本 ➔ 注意力稀释与遗忘 (Resolution Decay)**：长剧本塞满上下文导致大模型出现“长文本中间遗忘”，严重漏检微观动作的“小说化/不可拍文学描写”、角色跨场人设崩坏与跨场道具穿帮；
2. **人工手动分集复制 ➔ 流程繁琐且状态割裂**：人工切分并手动传递长文台账，极易丢失前情因果，无法形成严密的跨集长线逻辑追踪；
3. **JSON 状态机 ➔ 冗余 Token 浪费与外部配置门槛**：复杂嵌套 JSON 浪费 50%~70% 的 Token，且依赖外部 API Key 极易出现鉴权失效或网络阻断。

`script-reviewer v3.2.0` 采用 **“纯本地分章 + 原生多子 Agent 并发 + 纯 Markdown 滚雪球台账 + 批次写盘硬门禁 + 物理白皮书交付”** 的全自动工业闭环：

- **🎉 零外部 API Key 依赖**：完全复用 Antigravity 宿主原生大模型推理环境与鉴权，开箱即用，0 配置门槛；
- **📂 100% 物理落盘保障**：内置专用分章与写盘引擎（`script_splitter.py` / `batch_writer.py`），切片剧本、分集报告、增量日志、四大台账与终极白皮书全量物理落盘；
- **⚡ 原生多智能体并发矩阵**：通过 `invoke_subagent` 同时唤醒场记、剧情、心理、制片四大专家独立把关，反应式事件驱动，绝无低效轮询；
- **📊 纯 Markdown 高密度状态机**：彻底剔除冗余 JSON 语法，Token 节省 50%~70%，支持台账演进四大铁律与锁定标记（`[LOCKED]`）；
- **📸 智能自适应里程碑快照**：无论采用每批 1 集、2 集、3 集还是 4 集推进，系统自动在跨越满 10 集里程碑节点时归档备份总台账；
- **🛠️ 双向代码级 Patch 引擎**：针对跨集逻辑矛盾，同时输出“前向修补（改前文铺垫）”与“后向修补（改当前场次闭环）”代码级 Unified Diff。

## ⚡ Antigravity 原生多智能体并发调度协议

### 🚨 智能体协同四大红线与执行门禁 (Anti-Bypass Rules)

1. **严禁 Lead Agent 越权代写**：Lead Agent 严禁在自身主上下文中直接输出或通过编写/运行本地 Python 脚本批量伪造生成 4 大专家的分集审查报告；
2. **必须真实触发 `invoke_subagent`**：针对每一个切分章节 `ep_i.md`（$i = 1 \dots N$），必须调用 `invoke_subagent` 真实唤醒 4 个独立的专家子 Agent，并等待接收系统推送的真实审查报告；
3. **🚨 批次写盘硬门禁 (Batch Execution Gate · 阻断卡点)**：
   - 每接收完一个批次（1~3集）的 4 位子 Agent 审查报告后，**必须在当前回合立即调用 `batch_writer.py` 完成分集报告、增量日志与总台账三步物理落盘！**
   - **在未完成当前批次物理落盘与台账演进之前，严禁调用 `invoke_subagent` 派发下一个批次！** 若跳过写盘直接推进下一批，判定为严重违规；
4. **⚡ 严禁 `schedule` 轮询与主动 sleep**：
   - Antigravity 具备原生事件驱动唤醒机制。每次调用 `invoke_subagent` 后，**严禁调用 `schedule` 工具或运行 sleep 命令进行轮询**；
   - 只需在简要回复中说明“已派发，等待专家评审”，**不调用任何工具直接结束当前回合**。当子 Agent 完成并回传消息时，系统会自动唤醒主 Agent 继续执行写盘。

## 📊 纯 Markdown 高密度状态机与五大核心台账

为彻底消灭 JSON 冗余语法带来的 50%~70% Token 浪费，插件全流程统一采用 **高密度纯 Markdown 表格** 维护在 `.script_review_workspace/<剧本名>/ledgers/global_ledgers.md` 中。

### ⚡ 台账演进四大铁律 (Golden Rules)
1. **全量继承，严禁丢行**：历史轮次记录的所有条目（含已闭环 `[✓]`、待回收 `[+]`/`[⚠️]`、锁定 `[LOCKED]`）必须 100% 完整保留在表中，严禁删除历史行；
2. **ID 严格单调递增**：新项 ID 必须按最大已有 ID 顺延（如 `F-01`, `F-02` ➔ `F-03`），严禁断号或重复编号；
3. **锁定项不可篡改**：凡带有 `[LOCKED]` 标记的条目，后续轮次强制作为不可撼动的基准设定，严禁篡改；

## ❓ 常见问题与实战技巧 (FAQ)

### Q1：为什么不需要配置任何 `GEMINI_API_KEY` 或外部第三方服务？
> **答**：`script-reviewer v3.2.0` 是 Antigravity 原生扩展，它直接依托 Antigravity 会话的宿主大模型环境与上下文。分章与批次写盘工具（`script_splitter.py` / `batch_writer.py`）均为 100% 纯本地 Python 脚本（仅使用标准库），无任何第三方云端 API 依赖，零配置开箱即用。

### Q2：如何进行断点续审 (Resume)？
> **答**：系统在每次写盘时均会将分集报告保存在 `.script_review_workspace/<剧本名>/reports/report_ep_*.md`。若审查因网络或会话中断，再次发起时 Lead Agent 会自动扫描该目录已完成的集数，毫秒级跳过已审集数，无缝从第 $k+1$ 集继续推进。

### Q3：为什么台账中支持 `[LOCKED]` 锁定标记？
> **答**：主创人工确认过的关键核心伏笔、不可更改的人设基准或前置设定打上 `[LOCKED]` 标记后，后续各轮增量审查将强制将该条目作为不可撼动的既定事实，有效防止模型在长程推理中推翻已有共识或产生幻觉。

### Q4：为什么严禁 Lead Agent 用单一大脚本替代子 Agent？
> **答**：多智能体管线的核心力量在于**不同专家视角的对抗性与显微镜级别的专注力**（场记扣站位轴线与道具状态机、剧情扣因果闭环与戏剧压力、心理扣潜台词与位阶、制片扣政策红线与预算）。如果由 Lead 单模型兼任，模型会不可避免地产生长文本注意力分散与审美钝化。因此管线强制必须通过 `invoke_subagent` 真实唤醒 4 位独立子 Agent。

### Q5：为什么白皮书要求直接落盘在工作区根目录？
> **答**：终极白皮书 `final_whitepaper.md` 是全剧宏观层面的最高总结交付物。将其直接放置在 `.script_review_workspace/<剧本名>/` 根目录下，与 `episodes/`、`ledgers/`、`reports/` 三大目录同级并列，层次分明，最利于影视制片团队快速定位与查阅。
